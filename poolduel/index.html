5. Fairness and threats to validity (summary)

  • One harness, identical adapter contract: same timeouts, warmup, JSON schema, failure semantics. Adapters differ only in config_text() and port.
  • Same runner image, same PG build and config, freshly initialized dataset per run, interleaved round-robin order, medians over repeats, per-chunk direct control.
  • Every non-default pooler setting cites that pooler's own tuning docs in docs/configs/; anything uncited fails review.
  • Best-vs-best per workload plus iso-region slices on shared axes (clients {50,100,200}, backends {10,20}); surface flatness reported with peaks.
  • Threats: shared-runner variance (handled by medians, never static baselines); pgpool-II session-class-only comparison is labeled, not hidden; prepared-statement SQLSTATE 26000 fails the arm cell while the simple twin still compares; churn and prepared twins are always paired. Full text: docs/methodology.md.
  • Anti-theater checklist enforced: no home-team tuning, no sabotage by omission, no cherry-picked workloads, no hidden failures, no interpolated N/A, no carried-forward numbers across upgrades.

6. Reproduce it (one command)

./poolduel/repro.sh --dry-run   # print the pilot plan, run nothing
./poolduel/repro.sh --pilot     # M1-1 + M1-2, one repeat per arm
./poolduel/repro.sh --full      # all 9 M1 chunks (a1,a2,b1,b2,c,d,e,f,g)
THREADS=4 OUT=poolduel/results/m1 ./poolduel/repro.sh --full

Requires pgbench plus psql from PostgreSQL 17. repro.sh runs the preflight guard first (poolduel/harness/check.py: binaries, ratio guards, chunk caps) and fails loudly instead of running a compromised sweep.
